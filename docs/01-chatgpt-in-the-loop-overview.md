# Vibing Coding in the Loop：让 ChatGPT 边聊代码边测试

以前用 ChatGPT 辅助写代码时，最早的工作方式很原始：先在聊天框里讨论和修改代码，再把代码复制到本地文件里运行；如果报错，就把错误信息再复制回 ChatGPT，让它继续修改。如此反复。后来 Codex 这类 coding agent 出现以后，体验一下子好了很多。它不只是改代码，还可以直接在本地运行、测试，根据结果继续修正，甚至可以通过手机远程指挥。从设计、编码到测试可以一路自动做下去。实现真正的Vibing Coding——开发者动动嘴，Agent跑断腿。

但是我很快又碰到了新的限制：这种模式太烧大模型额度。Codex 很好用，但是5个小时额度可能一小时就用完进入冷却时间，于是会出现一种很尴尬的状态——我仍然可以在 ChatGPT 里继续讨论架构、分析问题、修改代码。但代码改完以后，却没法马上进入“运行—测试—继续修正”这个循环。对于真正的软件开发来说，很多问题只有运行以后才会出现，比如命令名写错、依赖版本不兼容、数据库虽然启动了但应用连不上，或者几个模块单独都正常，合在一起却失败。

后来我又发现，ChatGPT 的聊天模式其实可以利用插件和 GitHub 连接。既然代码已经放在 GitHub 上，那么完全可以利用 GitHub Actions，在每次代码修改以后自动运行测试。这样一来，ChatGPT 负责理解问题和修改代码，GitHub Actions 负责把代码放进真实环境里验证，测试失败以后再根据日志继续分析。原来需要人不断“复制代码到本地运行，再把报错复制回来”的过程，就可以自动化掉很大一部分。

问题是，这种模式实际使用中又会碰到下一层限制：GitHub-hosted runner 同样不是无限资源。如果频繁跑测试、编译和集成测试，Actions 的分钟额度也会很快消耗掉。于是思路自然走到了下一步：既然 GitHub 已经把 工作流、日志和调度都做好了，真正缺的只是执行计算，那为什么不把执行机器换成自己的？这就是后来想到 self-hosted runner 的原因。

这篇文章介绍的a方案并不是让 ChatGPT 获得一台可以随意控制的远程电脑，也不是让它自动把程序部署到正式环境。它解决的是开发过程中的自动验证环节——ChatGPT 负责分析和修改，CI 负责运行和测试，失败结果再进入下一轮分析。人仍然控制整个开发过程，只是原来最机械、最重复的那部分测试工作被接了起来。

## 1. GitHub不只是一个放代码的网站

很多非开发者第一次接触 GitHub，会把它理解成“程序员上传源码的网站”。这个理解没有错，只是不完整。对一个持续开发的软件项目来说，GitHub 更像是代码的中央仓库。你可以从不同电脑修改代码，每一次修改都有记录，也可以知道某个版本是谁改的、什么时候改的，必要时还可以回到之前的版本。

这件事对 ChatGPT 辅助开发很重要。如果 ChatGPT 只是把一段修改后的代码贴在聊天窗口里，那仍然更像一份建议；当修改真正进入 GitHub 仓库以后，它才进入项目正式的版本管理流程。

GitHub 还有一项非常重要的能力，叫 GitHub Actions。可以把它理解成 GitHub 自带的自动任务系统。你可以提前规定：每次代码发生变化以后，自动安装依赖、运行测试、构建 Docker、启动数据库或者检查应用是否能够正常启动。

这时，GitHub 做的事情就不只是保存代码。它还负责发现代码变化、触发测试任务、记录每一步执行结果，并保存成功或失败的日志。

GitHub Actions 本身负责的是“什么时候应该做什么”。真正执行这些命令的机器叫 runner。默认情况下，这台机器可以由 GitHub 临时提供。也就是说，GitHub 本身其实已经能够完成我们需要的自动测试流程。

问题并不是 GitHub 不能测试代码，而是当测试越来越频繁、项目越来越多以后，默认的执行资源是否还适合长期使用。

## 2. GitHub 为什么需要 Self-hosted Runner？

GitHub 默认提供的执行机器通常被称为 GitHub-hosted runner。对于小项目或者偶尔执行的任务，它非常方便：不需要自己准备 Linux，不需要维护机器，任务运行完成以后环境也会被回收。

但如果你长期开发多个 private repository，而且每次修改都希望运行 pytest、Docker build、数据库启动和 integration test，使用量就会不断增加。GitHub-hosted Actions 对私有项目存在套餐额度和计费规则，测试越重、运行越频繁，占用的时间就越多。多个项目同时开发时，这些消耗也会累积。

除了费用和额度，GitHub-hosted runner 还有另一个特点：运行环境由 GitHub 提供和管理。对于一般 CI 这反而是优点，因为环境比较干净；但如果你的项目需要固定工具链、长期 Docker cache、特殊系统依赖或者更稳定的本地环境，每次使用临时机器就未必最方便。

如果家里本来就有长期在线的 NAS、服务器、mini PC，或者已经有一台 VPS，就有了另一种选择：GitHub 继续负责 Actions、日志和任务调度，但真正执行测试的机器换成自己的。

这就是 self-hosted runner。

Self-hosted runner 并没有替代 GitHub Actions。GitHub 仍然负责保存代码、触发 workflow、记录测试状态和保存日志，只是测试计算不再发生在 GitHub 临时提供的机器上，而是在我们自己的 Debian 主机上。

从这个角度看，我们并没有重新发明 CI，也没有绕开 GitHub。我们只是把“执行测试的计算资源”从 GitHub-hosted 换成了 self-hosted。

## 3. 搭建一套隔离的自动验证环境

这里很容易产生一个误解：既然代码最终会在自己的机器上运行，是不是等于把服务器直接交给 ChatGPT？

不是。

在这套方案里，ChatGPT 不需要 SSH 登录 CI 主机，也不需要直接操作正式服务器。它修改的是 GitHub 里的代码，而 GitHub Actions 按照我们提前写好的 workflow 去执行测试。Self-hosted runner 只是按照 workflow 接任务并运行这些测试命令。

这和“让 AI 随意登录服务器执行任何命令”是完全不同的两种模式。

我自己的做法是在正式 Unraid 环境旁边单独准备一台 Debian VM，专门跑 CI。这个 VM 可以安装 Docker、Python 和测试需要的工具，但不挂载正式的 appdata，不暴露 Unraid host 的 Docker socket，也不放真实交易 API Key、生产数据库密码或者其他生产环境凭证。

这样做的目的不是说这个 VM 永远不会出问题，而是把风险和影响范围限制在一个专门用于测试的环境里。CI 可以失败，可以留下错误日志，可以重新执行，但它不应该因为一次普通测试就影响正式服务。

我更愿意把它理解成一间实验室，而不是一条生产线。ChatGPT 参与的是提出修改和分析结果，GitHub 负责把修改送进实验室，self-hosted runner 负责按规则做实验。真正的生产部署仍然是另一件事，应该有另外的权限和流程。

这一点也说明了为什么我们要把“自动测试”和“自动部署”分开。前者的目标是尽快发现错误，后者涉及正式环境、用户数据和真实服务，两者的风险完全不同，不应该混为一谈。

## 4.一个更完整的 AI 辅助开发循环

把这些东西接起来以后，开发方式发生的变化其实很简单。

以前，ChatGPT 改完代码以后，往往需要人自己运行测试，然后把错误复制回来。现在，代码修改进入 GitHub 以后，可以自动触发 Actions，由 self-hosted runner 在真实 Linux、Docker、数据库和项目依赖环境中执行测试。测试成功，说明这次修改至少通过了我们预先设定的验证；测试失败，则会留下真实错误和日志，供下一轮分析。

所以这套系统真正形成的是一个“修改—测试—反馈—继续修改”的循环，而不是“ChatGPT 直接运行和部署软件”。

ChatGPT 负责理解问题、提出修改和分析错误；GitHub 负责版本管理和任务调度；self-hosted runner 提供真实测试环境；CI logs 提供验证结果；人仍然决定哪些修改可以接受、什么时候继续、什么时候进入正式环境。

这也是它和 Codex、Claude Code 或其他 coding agent 不完全一样的地方。那些工具主要解决 AI 怎样更主动地读代码、写代码和修改代码，而这里解决的是另外一层问题：**无论代码是谁改的，怎样让这些修改持续进入真实环境接受验证。**

从这个角度看，self-hosted runner 不是给 ChatGPT 增加“服务器控制权”，而是给 AI 辅助开发增加一个低成本、可重复、相对隔离的自动测试层。
