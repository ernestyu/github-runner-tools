# Vibing Coding in the Loop：让 ChatGPT 边聊代码边测试

几年前开始用 ChatGPT 写代码时，方法很笨拙：在聊天框里让它帮我写或者改一段代码，然后把代码复制到自己的电脑上运行。如果报错，就把错误信息再复制回 ChatGPT，让它继续分析和修改。改完以后再运行，再把新的结果贴回来。整个过程就是“聊天—复制—运行—报错—再聊天”，不断循环。

后来出现了 Codex 这类 coding agent，体验一下子变了。和普通聊天不同，coding agent 不只是告诉你代码应该怎么改，它还可以直接进入本地代码目录，修改文件、运行程序、执行测试，再根据测试结果继续修正。对开发者来说，这非常接近理想状态：你负责描述目标和判断方向，Agent 负责大量具体操作。从设计、编码到测试，很多事情可以一路做下去，这也是现在大家常说的 Vibing Coding。

实际用了一段时间以后，碰到一个很现实的问题：这种方式极度消耗大模型额度。Codex 很好用，可一旦额度用完进入冷却时间，开发过程就会突然断掉。这时候 ChatGPT 的普通聊天还可以继续用。我仍然可以和它讨论架构、分析问题、甚至通过插件让它修改 GitHub 仓库里的代码，不过却少了 coding agent 最重要的一环：代码改完以后，马上在真实环境里运行和测试。软件开发并不是“把代码写出来”就结束了。很多错误只有真正运行以后才会出现：一个命令可能拼错了，某个软件库版本可能不兼容，数据库虽然启动了但程序连不上，几个模块单独都正常，组合在一起却失败。人类程序员写完代码以后也要运行和测试，AI 当然也一样。

既然 ChatGPT 还能继续负责分析和修改代码，那能不能把“运行和测试”这件事交给另一个系统自动完成？

## 1. GitHub 不只是存代码

很多不写程序的人听说过 GitHub，但通常会把它理解成“程序员放源码的网站”。这个理解不算完整。更简单地说，GitHub 可以把一个软件项目的代码和文档集中保存起来，并记录每一次修改。你可以在家里的电脑上改，也可以在另一台电脑上改，最后都回到同一个项目里。哪一天改了什么、谁改的、出了问题能不能退回以前的版本，GitHub 都能记录。

这对 ChatGPT 很重要。因为如果代码只存在聊天框里，它更像是一段建议；如果 ChatGPT 修改的是 GitHub 里的项目，那这些修改就真正进入了软件项目本身。因为每一次修改都有记录，每一步都可以回溯。更关键的是，GitHub 还有一个功能叫 **GitHub Actions**。普通读者可以把它理解成“代码仓库旁边自带的一套自动任务系统”。你可以提前告诉 GitHub：只要代码发生变化，就自动做一些事情，比如安装程序、运行测试、检查程序能不能启动，或者构建 Docker。

这类自动检查在软件开发里通常叫 **CI**，也就是 Continuous Integration，中文常译成“持续集成”。名字听起来很专业，但它做事规则很简单：**每次代码有变化，就自动检查这次修改有没有把项目弄坏。** 这样一来，原来必须由人手工完成的一部分工作，就可以交给 GitHub。ChatGPT 修改代码，代码进入 GitHub，GitHub Actions 自动运行测试。如果测试失败，GitHub 会留下错误日志，我们再把这些真实结果拿回来继续分析。

换句话说，普通 ChatGPT 即使不能像 Codex 那样直接在本地运行代码，也可以借助 GitHub 把“修改以后自动测试”这一环接回来。

## 2. GitHub 干活需要一台电脑

GitHub Actions 虽然能自动安排测试，但这些测试总要在一台真正的电脑上运行。GitHub 默认会临时提供这样的机器。软件开发里把这种负责执行任务的机器叫 **runner**。如果机器是 GitHub 提供的，就叫 **GitHub-hosted runner**。你可以把它想成 GitHub 临时借给你的一台 Linux 电脑：任务来了就启动，按照 workflow 里的要求运行测试，结束以后再回收。这种方式非常方便，因为你不用自己准备机器，也不用维护系统。对于偶尔跑几个测试的小项目，它几乎没有学习成本。

但我很快又碰到了熟悉的问题：GitHub-hosted runner 也不是无限资源。尤其是不公开的私人代码仓库，如果频繁运行测试、编译、Docker build 和 integration test，就会不断消耗 GitHub Actions 的运行时间。项目一多，测试一频繁，额度同样会变得紧张。结果又变成要么付费，要么另外想办法。不过，既然 GitHub 已经帮我解决了最麻烦的部分——代码仓库、任务触发、运行流程、测试结果和日志——真正缺的其实只是一台不会限制运行额度，负责执行任务的电脑。那为什么不让 GitHub 把任务发到自己的电脑上运行？这就是 **self-hosted runner**。名字看起来复杂，其实意思非常简单：GitHub 继续负责发任务，但负责干活的机器不再由 GitHub 提供，而是换成自己的服务器、NAS、mini PC、虚拟机或者 VPS。

这套方案并不是重新做了一套 CI，也不是绕开 GitHub。GitHub Actions 还是原来的 GitHub Actions，只是把“执行测试的电脑”从 GitHub 的机器换成了自己的机器。

## 3. 自动测试无须让 ChatGPT 控制服务器

这里有一个很容易误解的地方。把 self-hosted runner 接进来，并不等于 ChatGPT 获得了一台远程服务器，更不等于它可以随意登录机器、执行任何命令或者把代码直接部署到正式环境。

在这个方案里，ChatGPT 仍然主要负责聊天、分析和修改代码。它修改的是 GitHub 里的项目。GitHub Actions 看到代码变化以后，按照事先写好的规则去触发测试。Self-hosted runner 收到任务后，只负责在自己的测试环境里运行这些预先定义好的步骤。也就是说，真正的关系是：ChatGPT 提出修改，GitHub 管理代码和任务，runner 负责执行测试，人仍然决定下一步怎么办。

为了进一步降低风险，我没有让 runner 直接跑在正式服务器环境里，而是在自己的服务器里单独建了一台 Debian 虚拟机。你可以把虚拟机理解成“服务器里的另一台小电脑”。它和正式服务隔开，专门用来做 CI 测试。这台 Debian 可以安装 Python、Docker、数据库和测试工具，但不需要拿到正式业务的全部权限。它不应该保存生产数据库密码，不应该拿真实 API Key，也没有必要直接控制宿主机的 Docker。我更愿意把它理解成一间实验室。代码先到实验室里运行、测试、失败、重试。真正的生产环境是另一件事，应该有另外的发布流程和权限。

## 4. 一个更完整的 AI 辅助开发循环

这个方案其实不是一开始设计出来的，而是在一次次碰到限制以后慢慢琢磨出来的。最早只有 ChatGPT 聊天，于是代码要人工复制到本地运行；后来 Codex 让 AI 能直接修改、运行和测试，但大模型额度又成了新的限制；再后来发现普通 ChatGPT 可以连接 GitHub，于是 GitHub Actions 可以接手自动测试；继续用下去以后，又发现 GitHub-hosted runner 同样有资源和额度问题，于是最后把执行机器换成了自己的 self-hosted runner。

最终得到的并不是“ChatGPT 会直接操作我的服务器”，而是一个更顺畅的开发循环：ChatGPT 负责理解需求、分析问题和修改代码；GitHub 负责保存版本、触发任务和记录结果；自己的 runner 负责真正运行测试；测试失败后，错误日志再进入下一轮分析。原来最麻烦的那段“把代码复制到本地、运行一下、把报错复制回来”的工作，被自动化掉了大部分。

人仍然在这个循环里，而且仍然做最重要的判断：需求是什么，修改方向对不对，测试结果能不能接受，什么时候该继续，什么时候可以发布。自动化只是把最机械、最重复的验证工作接起来。从这个角度看，self-hosted runner 并不是给 ChatGPT 增加服务器控制权，而是给普通 ChatGPT 增加了一条通往真实测试环境的桥。

真正把这套方式跑起来以后，我又碰到一个很实际的问题：如果只有一个项目，按照 GitHub 的说明注册一台 self-hosted runner 并不复杂；但如果个人账号下面有很多私有仓库，每增加一个项目，都要重新下载 runner、注册、设置名称和标签、安装系统服务，再检查它是否正常运行。这些事情本身并不难，只是非常重复。所以我把这部分整理成了一个小工具 **github-runner-tools**。它不是另一套 CI 系统，也不会替代 GitHub Actions，只是把“给一个 GitHub 仓库增加 self-hosted runner”这件事尽量标准化。准备好一台 Debian/Linux 主机以后，给一个新仓库增加 runner，基本只需要运行一条脚本，再粘贴 GitHub 临时生成的授权码，剩下的下载、注册、systemd 服务和状态检查由脚本完成。

下一篇再具体讲怎么搭这套系统的开源地址，部署环境：准备 Debian、安装 runner、把 GitHub Actions 接到自己的机器上，并让一个私有仓库真正开始自动测试。
