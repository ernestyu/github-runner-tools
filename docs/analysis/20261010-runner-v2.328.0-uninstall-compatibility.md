# GitHub Actions Runner v2.328.0 — Offline Service Uninstall Compatibility Evidence

Scope: **source-level and isolated execution proof**, not real Debian runner acceptance. Frozen SPEC: `24ee31c786e6dee6b7e0305e284b571f31e0eb8e`. This document adds no new runtime compatibility promise or authorization.

## Source authority and pin

Official repository: `actions/runner`, **tag `v2.328.0`** (obtained from GitHub tag's recursive Git tree and raw source); original `src/Misc/layoutbin/systemd.svc.sh.template`, pinned Git blob **`8429854293708c0657822e5625cb7f2b61903871`**. Byte-identical source is stored as `tests/fixtures/actions-runner-v2.328.0-systemd.svc.sh.template`, and its Git blob SHA is checked by `tests/test-runner-version-compatibility.py`. Additional source: [ConfigurationManager.cs](https://github.com/actions/runner/blob/v2.328.0/src/Runner.Listener/Configuration/ConfigurationManager.cs) (lines 508–535) and [ServiceControlManager.cs](https://github.com/actions/runner/blob/v2.328.0/src/Runner.Listener/Configuration/ServiceControlManager.cs) (CalculateServiceName).

## Observed official code behavior

`svc.sh` is created from `systemd.svc.sh.template` with generated `SvcNameVar`. Its `uninstall()` (template lines 117–130) stops the existing service, disables it, removes the Unit, **removes `.service`**, then executes `systemctl daemon-reload`. If the Unit is already missing, it still removes `.service` when present. The template's `CONFIG_PATH=.service` is direct evidence that this record is an official uninstall postcondition. This is precisely the state omitted by the old Web Dispatcher.

Official `ConfigurationManager.UnconfigureAsync()` checks `_store.IsServiceConfigured()` and, on Linux, throws `Uninstall service first` *before* server deregistration. Therefore the local service record's disappearance is a necessary prerequisite for `config.sh remove`, not evidence of successful GitHub server deregistration.

Service name: the official `ServiceControlManager.CalculateServiceName()` replaces characters outside `[0-9A-Za-z._-]` in RepoOrOrgName and interpolates the configured AgentName into the service-name pattern. It uses truncation plus a random suffix if the name exceeds 150 characters. The existing Dispatcher `canonical_service_name` accepts only **non-truncated, exact** names up to 150 characters and rejects foreign/mismatched names. For this pinned fixture `example/repo` and `fixture`, generated identity `actions.runner.example-repo.fixture.service` is within the limit and matches the canonical format. This does **not** prove every automatically generated name or every repository-scope variant is compatible; those must fail closed under existing identity validation.

**Version-specific important limitation:** official v2.328.0 `install()` template sets the Unit to mode **664** (line 91). The existing root Dispatcher rejects group-writable Units, so a freshly official-installed Unit requires an explicitly approved permission correction (to 644) before the strict Dispatcher can manage it. This implementation does not silently relax the Dispatcher safety requirement. Compatibility here is conditioned on successful existing Unit validation.

## Offline execution evidence

`tests/test-runner-version-compatibility.py` executes the *real pinned `uninstall()` function* with only test-specific replacements for the fixed Unit path and service template placeholders; shell `systemctl` and `id -u` are redirected to disposable shims. It asserts that the fake Unit and `.service` are absent, while `.runner` and `.credentials` are untouched, and verifies `stop`, `disable`, and `daemon-reload` calls. No production `systemctl`, root operations, GitHub API, or registration tokens are used.

Dispatcher+reconciliation has the same **relevant local prerequisite** after verified Unit removal and safe quarantine of `.service`: Unit absent and `.service` absent. The strategies are *not* claimed identical in privilege model, intermediate file states, or error behavior (our reconciliation intentionally retains quarantine until confirmed remote unregister).

## Untested versions and non-guarantees

Only upstream v2.328.0's template and Linux UnconfigureAsync code are pinned and covered. This is **not** proof for later/earlier runner versions, patched forks, exotic service template conventions, custom service names, or OS variants. Such deployments have no guaranteed compatibility. If the complete generated service name differs, identity, Unit provenance or record validation must reject rather than guess. Production acceptance must separately establish the installed Runner binary/script version and compare its local `svc.sh` / service state without changing production.

Evidence is for the **service-uninstall prerequisite** only; it does not make real GitHub remote deregistration succeed or authorize production Remove.
